A **checkpoint** is a coherent snapshot of a thread after a superstep barrier:
channel values, run status, interrupt payload if any, enough bookkeeping to
continue.

Without checkpoints, voluta would be an in-process state machine. With them, a
run can **pause, survive restart, and resume** under the same `ThreadId` —
including from another process.

## Why after every barrier?

Because that is when state is **consistent**:

- all node tasks for the tick finished  
- writes were merged through reducers  
- edges have not yet started the next tick (or the run stopped)

Checkpointing mid-handler would freeze half-thoughts. Checkpointing only at
process exit loses the “human approved three hours later” story.

## The only storage seam: `ICheckpointer`

```csharp
Task PutAsync(CheckpointSnapshot snapshot, CancellationToken cancellationToken = default);
Task<CheckpointSnapshot?> GetAsync(string threadId, CancellationToken cancellationToken = default);
Task<IReadOnlyList<CheckpointSnapshot>> ListAsync(string threadId, CancellationToken cancellationToken = default);
```

| Method | Contract |
|--------|----------|
| `PutAsync(CheckpointSnapshot)` | Persist this **full** C-shape snapshot. There is **no** `putWrites` |
| `GetAsync(threadId)` | **Latest** snapshot only, or **null** if never written (miss does not throw) |
| `ListAsync(threadId)` | **Full** history, oldest step first. If you can’t list, throw `NotSupportedException` — never a silent partial |

InMemory, File, EF, S3, and Redis all implement history. Channel edits from a host are
`CompiledGraph.UpdateStateAsync(threadId, IEnumerable<ChannelWrite>)` — not a checkpointer
method. Host reads: `GetStateAsync` (latest `ThreadSnapshot`) / `GetHistoryAsync` (all
steps). Those façade methods are available but still Unshipped.

`IVolutaStore` is a different seam (cross-thread KV). Its `ListAsync(namespace)` lists
**all keys in that namespace**, not checkpoints.

Optional **thread discovery** (ops UI, multi-host): implement
`IThreadDiscovery.ListThreadIdsAsync` on the same type as `ICheckpointer`.
`VolutaUiSession.ListThreadsAsync` merges discovery ids with in-process
`TrackThread` so a restarted host can list durable threads without re-tracking.

| Provider | How threads are enumerated |
|----------|----------------------------|
| File | Child directories under the checkpointer root (one dir per sanitized thread id) |
| EF Core | `SELECT DISTINCT ThreadId … ORDER BY ThreadId` on the checkpoints table |
| S3 | `ListObjectsV2` with `Delimiter=/` under the key prefix (CommonPrefixes) |
| InMemory | Keys already present in the process-local dictionary |

Your app should depend on the interface. Swap in-memory → file → future store
without rewriting nodes.

## What a snapshot carries

| Field | Why it exists |
|-------|----------------|
| `ThreadId` | Isolation between conversations / jobs |
| `Step` | Superstep index — ordering and debugging |
| `Status` | `Done` / `Interrupted` / `Failed` / … |
| `ChannelValues` | The actual graph state |
| `InterruptPayload` | What to show a human when paused |
| `PendingSends` / `PendingWrites` | Mid-run recovery details |

You rarely construct these by hand — the runtime does. You *read* them for ops
UIs, support tools, and tests.

## Providers

| Provider | Package | Registration | When to use |
|----------|---------|--------------|-------------|
| In-memory | `Voluta` | `UseInMemory()` | Tests, samples, single process |
| File (JSON on disk) | `Voluta.Checkpoints.File` | `UseFile(root)` | Simple single-node durability |
| Redis | `Voluta.Checkpoints.Redis` | `UseRedis(…)` | Shared store across replicas |
| **EF Core** | `Voluta.Checkpoints.EntityFrameworkCore` | `UseEntityFrameworkCore<TDb>()` | **Any DB EF supports** (SQL Server, Postgres, SQLite, …) with *your* DbContext |
| S3 / compatible | `Voluta.Checkpoints.S3` | `UseS3(o => …)` | Object storage |

Native Sqlite / Postgres packages were dropped in 0.3.0 — use File, Redis, EF, or S3.

```csharp
services.AddVoluta(v =>
{
    v.Checkpoints.UseFile("/var/lib/myapp/voluta-checkpoints");
    // or: v.Checkpoints.UseEntityFrameworkCore<MyDb>();  // any EF provider
    // or: v.Checkpoints.UseRedis(o => o.ConnectionString = "…");
    v.Graph((sp, checkpointer) => /* … */ .Compile(checkpointer));
});
```

Provider types are constructed via `Use*` only — not `new` from app code.
Prefer JSON-friendly channel values (strings, numbers, lists of primitives).
**Durable rehydrate is lossy at the store:** File / EF / S3 / Redis `FromElement`
restores `string` / `bool` / `long` / `double` and arrays as `List<object?>`. JSON
objects (`{}`) become `GetRawText()` — a JSON **string**, not the original CLR type
and usually not `JsonElement`. InMemory keeps CLR references (no JSON).

Declare `AddChannel<T>` (or `[GraphState]` property types) so the **compiled graph**
coerces those wire values on restore (`int` stays `int`, append strings stay
`string`). Untyped channels keep the wire shapes. Custom POCOs still fail Put with
`checkpoint.unsupported_value_type` (wire v1 allow-list) unless they are
dictionaries / lists of primitives.

In-memory is not “fake voluta.” It is the same protocol with a store that dies
with the process — fine until durability is a product requirement.

## Testing storage without lying

`Voluta.Testing` exists so you don’t invent half-broken doubles:

- `RecordingCheckpointer` — see every put/get/list  
- `FaultInjectingCheckpointer` — fail the *n*-th write; assert the run survives or fails cleanly  
- `CheckpointerConformance.RunAllAsync` — the suite **your** `ICheckpointer` should pass, interrupt fields included  

If you implement a new store, conformance is the bar — not a happy-path unit
test that never interrupts.

## Operational habits

1. **Stable thread ids** from your domain (ticket id, session id), not random per
   request unless you truly want a one-shot run.  
2. **Treat Interrupted as normal** — poll or webhook → `ResumeInvokeAsync`.  
3. **Don’t hand-edit checkpoint files** in production; use the API and UI.
